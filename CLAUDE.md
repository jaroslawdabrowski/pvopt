# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A home energy management app: reads battery SOC from a Deye hybrid inverter over the local network, pulls PV production forecast from Forecast.Solar (up to 4 panel planes, one per compass direction), and makes exactly **two decisions a day** — matching PGE G12's two cheap tariff windows — on whether to charge the battery from the grid: one for the overnight window (default 21:45, for 22:00–06:00, using tomorrow's forecast) and one for the short afternoon window (default 12:45, for 13:00–15:00, using the rest of today's forecast). Each decision is written to the inverter's own Time-of-Use schedule and logged for the frontend to display.

All of that — SOC thresholds, consumption estimates, the two decision times, the forecast install (location + per-direction panels), and the inverter connection — is **user-editable process settings**, stored as one JSON blob in the database and edited from the frontend's Settings page (`GET`/`PUT /api/settings`), not `application.properties`. Until settings are saved once, nothing runs: see "Process settings" below.

Monorepo: `backend/` (Quarkus, Java 21) + `frontend/` (Angular 21, standalone/signals). Quinoa builds the Angular app and serves it from the same Quarkus jar — one process, one port, meant to end up running on a LAN-only device (currently developed on macOS).

## Commands

Backend (run from `backend/`):
- `./mvnw quarkus:dev` — dev mode; Quinoa also starts `ng serve` and proxies frontend requests, so this alone gives you the full stack on `http://localhost:8080`.
- `./mvnw test` — full backend test suite.
- `./mvnw test -Dtest=ChargeDecisionPolicyTest` — single test class; `-Dtest=ClassName#methodName` for a single method.
- `./mvnw package` — builds `target/quarkus-app/quarkus-run.jar` (run with `java -jar target/quarkus-app/quarkus-run.jar`), embedding the built Angular app.

Frontend (run from `frontend/`, only needed standalone — normally Quinoa drives it):
- `npm start` / `ng serve` — dev server on `:4200` (won't have a working backend behind `/api` unless Quarkus is also running).
- `npm test` / `ng test` — Vitest unit tests.
- `npm run build` / `ng build` — production build to `dist/frontend/browser`.

Requires Node compatible with Angular 21's engine check (`^20.19.0 || ^22.12.0 || >=24.0.0`); Quinoa is configured with `quarkus.quinoa.package-manager-install=false` to use the system `node`/`npm` on PATH rather than downloading its own (a pinned older Node version there previously broke `ng serve` — don't reintroduce `package-manager-install=true` with an old `node-version` pin).

## Architecture

### Hexagonal, package-by-feature (not package-by-layer)

Everything lives under one bounded context, `energyplanning`, structured as domain → ports → application → adapters — deliberately not `service/`/`dao/`/`controller/` packages:

```
energyplanning/
  domain/       pure logic, zero framework annotations: BatteryStatus, ProductionForecast,
                TariffWindow/TariffRate/TariffCalendar (G12 window math, dashboard display only),
                ChargeWindow (OVERNIGHT/AFTERNOON), ChargeSchedule, DecisionReason, ChargeDecision,
                PlanningPolicyConfig, ChargeDecisionPolicy (the decision engine, called once per window),
                ProcessSettings + PlanningSettings/ScheduleSettings/ForecastSettings/
                InverterConnectionSettings/DirectionPanelSettings/CompassDirection (see below),
                ProcessSettingsNotConfiguredException
  port/in/      PlanOvernightChargeUseCase, PlanAfternoonTopUpUseCase, GetEnergyStatusUseCase,
                GetPlanningHistoryUseCase, GetTouScheduleUseCase, GetProcessSettingsUseCase,
                UpdateProcessSettingsUseCase
  port/out/     InverterPort (incl. readDailyEnergy), EnergyRecordPort, ForecastPort (productionProfile(period) - kWh per hour slot, settings-parameterized),
                PlanningHistoryPort, ClockPort, ProcessSettingsPort, SchedulingPort
  application/  EnergyPlanner — the only orchestrator for planning/status/TOU display; wires ports +
                domain, no business logic itself. ProcessSettingsManager — the settings orchestrator,
                saves + tells SchedulingPort to re-register the daily jobs
  adapter/in/   web/ (JAX-RS resources + exception mappers), scheduler/ (DynamicEnergyPlanningScheduler -
                programmatic Quarkus Scheduler jobs, not a fixed @Scheduled cron)
  adapter/out/  inverter/solarman/, forecast/forecastsolar/, persistence/, clock/
```

`ChargeDecisionPolicy` and `TariffCalendar` are tested with plain JUnit (no `@QuarkusTest`, no mocks) — that's intentional and is where the actual business rules live; if you change the charge/no-charge logic, start there. `platform/security/` (Basic Auth) sits outside the `energyplanning` hexagon as a cross-cutting platform concern.

`ChargeDecision` deliberately does **not** carry a rendered message — `ChargeDecisionPolicy` returns a `DecisionReason` enum value plus a `Map<String, Double> reasonParams` (e.g. `soc`, `minSoc`, `forecastKwh`, `requiredKwh`, `targetSoc`). Turning that into a sentence is the frontend's job (see i18n below); if you add a new branch to the policy, add the matching enum value and a `reason.<NAME>` key to *both* `frontend/public/i18n/en.json` and `pl.json`, with placeholders matching whatever keys you put in `reasonParams`. `PanacheChargeDecisionRepository` is the only place that knows the reason params are stored as a JSON blob (`reason_params_json` column) — that serialization detail doesn't belong anywhere else.

`ChargeDecisionPolicy.decide(...)` is a single pure function shared by both daily decisions — it takes `ChargeWindow`, a `ProductionForecast`, and an already-computed `requiredKwh`, not a tariff check or a "which window is this" branch internally. **Choosing what each window has to cover is `EnergyPlanner`'s job, not the policy's**: both decisions go through `EnergyPlanner.plan(window)`, which takes the *expensive period right after that cheap window* (`TariffCalendar.expensivePeriodAfter(calendar.windowFor(window), now)` - G12: 06:00-13:00 after the night, 15:00-22:00 after the afternoon; the overnight decision owns the window that crosses midnight) and weighs `PlanningSettings.consumptionAfter(window) * forecastSafetyMarginRatio` against `forecastPort.productionProfile(period)` - PV for exactly those hours, **hour by hour**: the consumption is spread over the period's hour slots by `HourlyConsumptionProfile` (the learned mean load per hour of day, flat until every hour of the period has ≥ 3 samples) and `PeriodBalance.of` takes the **largest running deficit** as the reserve (`reserveKwh`, peak time in `reservePeakHour`). Totals alone hid timing - on 2026-10-14 the morning PV total (4.9 kWh) almost covered 5.6 kWh, but the sun only caught up after 09:00, so the battery needed ~1.5 kWh, not 0.75. Anything the battery needs later is the next window's decision. The PV profile is first scaled by `ForecastCalibration` - measured PV / forecast PV (ratio of sums, ≥ 3 periods and ≥ 1 kWh forecast, clamped to 0.3-1.5) over the last 14 days of *that window* (east/west planes can be off differently morning vs evening), pairing each measured `PeriodOutcome` with the **raw** forecast (`forecastRawKwh`, or `forecastKwh` from before calibration existed) of the last decision for that period - never the calibrated one, or the correction would feed on itself. Reason params: `forecastRawKwh`, `calibrationFactor`, `calibrationSamples`; `forecastKwh` is the calibrated figure. The planner adds `periodFromHour`/`periodToHour` to the reason params (decisions recorded before this lack them - the frontend's `decisionPeriod()` handles that). `PlanningPolicyConfig` only holds battery facts (the two SOC thresholds plus `batteryCapacityKwh`) for exactly this reason — don't add window-specific fields to it. A grid charge targets only the shortfall: `minSoc + ceil(reserveKwh / batteryCapacityKwh * 100)`, capped at `fullSoc` (`ChargeDecisionPolicy.targetSocFor`) - charging further just fills room tomorrow's PV would have used, and under net-billing that surplus is exported for a fraction of its price. `batteryCapacityKwh == 0` means unknown (settings saved before the field existed deserialize to 0) and falls back to charging to `fullSoc`. **The decision doesn't depend on the SOC at decision time** (only the below-`minSoc` safety case looks at it): any shortfall means grid charge on with the reserve as target, and the inverter compares SOC with that target itself *during* the window - topping up only if the battery has drained below it by then, otherwise holding it there (the target is also the slot's floor), so cheap-hour load runs on the cheap grid instead of draining what the expensive hours need. Comparing with the SOC at decision time was wrong for any decision made ahead of its window (a manual overnight run at 14:00 with a full battery). With no shortfall the floor is `minSoc`. `batteryCapacityKwh` is the full 0-100% capacity, not the usable part above `minSoc` (the reserve is added on top of `minSoc`). `ALREADY_AT_TARGET_SOC` and `RESERVE_HELD` are kept only so older history rows still render.

### Reliability: retries, read-back, notifications

`DynamicEnergyPlanningScheduler.attemptDecision` retries a failed decision (any `RuntimeException` - logger unreachable, dropped frame) up to `MAX_ATTEMPTS` = 3, `RETRY_DELAY` = 3 min apart (the jobs run ~15 min before their window); only when all fail does `GuardChargeScheduleUseCase.reportFailure` record a `RunIssue` + notify - the inverter then keeps its previous schedule. After a decision goes through, `ScheduleGuard.verify` runs `VERIFY_DELAY` = 2 min later: reads the window's governed TOU slots back, compares them with the window's latest decision, rewrites **once** on a mismatch (the register-159 revert above) and reports `SCHEDULE_MISMATCH` if that doesn't fix it; skipped while `InverterPort.appliesWrites()` is false (dry run). Delayed tasks run on the adapter's own `ScheduledExecutorService` with the request context activated by hand (`Arc.container().requestContext()`) - Panache needs one and only scheduler/HTTP threads get it for free.

A failed forecast doesn't fail the decision: `EnergyPlanner.forecastOrNone` plans as if no sun were coming (a conservative grid charge), flags `forecastUnavailable=1` in the reason params and reports `FORECAST_UNAVAILABLE`. `IssueReporter` is the single place that records a `RunIssue` (`run_issue` table, latest one exposed as `latestIssue` on `GET /api/status` - the dashboard shows it for 24 h, and separately warns when the last decision is older than 26 h, i.e. the jobs aren't running) and pushes it via `NotificationPort` (`NtfyNotificationAdapter`: POST to the ntfy topic URL from `ProcessSettings.notifications` - optional, blank = off, older settings have none; title/priority as URL-encoded query params since ntfy headers would need RFC 2047 for Polish). Notification text is the one bit of user-facing copy the backend writes, worded per the persisted UI language (`GetLanguagePreferenceUseCase`). `POST /api/notifications/test` (body `{ntfyUrl}`) backs the Settings page's test button, so an unsaved URL can be tried.

### Measuring outcomes and learning consumption

`EnergyRecorder` (implements `RecordEnergySnapshotUseCase` + `GetLearnedConsumptionUseCase`) snapshots the inverter's daily energy counters + SOC every full hour plus at every cheap window boundary (`TariffCalendar.boundaryTimes()` - G12's are all full hours anyway; one programmatic `energy-snapshot-HH:mm` job each - the hourly ones feed `HourlyConsumptionProfile`, registered by `DynamicEnergyPlanningScheduler` alongside the two decision jobs). When a snapshot lands on the end of an expensive period (`TariffCalendar.expensivePeriodEndingAt`), the snapshot from the period's start (±15 min) is subtracted into a `PeriodOutcome` (load, PV, grid import/export, SOC at start/end) stored in `period_outcome`. The counters reset at the inverter's midnight, so a period crossing midnight is skipped (G12's never do). Every snapshot also re-measures any period of the last 3 days that ended, has snapshots at both ends and no outcome yet (`measureCompletedPeriods`) - so an outcome that failed to save is recovered on the next snapshot. `ConsumptionEstimator.learn` turns the last 14 days of a window's outcomes into a mean (needs ≥ 3) - but **never from before the user last changed that window's estimate** (`PlanningSettings.learnFrom`): a changed estimate means the house uses energy differently now (on 2026-10-15 the heating's controls and pump group went on and both estimates went up), and the summer's lower figures shouldn't pull the learned value back down for two weeks. `ProcessSettingsManager.updateSettings` fills `consumptionAfter{Overnight,Afternoon}ChangedAt` by comparing with the stored settings (`PlanningSettings.withChangesSince` - the form never sends them; an unchanged value keeps its old date, the very first save sets none); `GET /api/energy/learned-consumption` reports `{kwh|null, samples, countingFrom}` so Settings can say "counting afresh since …: 1 of 3". It which `EnergyPlanner.plan` uses instead of the settings estimate (reason params `consumptionKwh`/`learnedSamples`). `GET /api/history` returns each decision with its period's `outcome` (matched by re-deriving the period from `decidedAt` + window - null if the period isn't over or the tariff windows changed since); `GET /api/energy/learned-consumption` backs the "Zmierzone: ..." line on the Settings page.

The six daily counter registers (`SolarmanInverterConfig.daily*Register`, 514/515/520/521/526/529, 0.1 kWh, read as one 514-529 block) were **confirmed on real hardware** by an exact energy balance (PV + bought + discharged = load + sold + charged, to 0.1 kWh) - this inverter uses the 3-phase SG04LP3 map, not the single-phase one (where 70-108 hold these; here those are settings: 99-101 charge voltages, 102 battery capacity in Ah).

There is a second, much smaller bounded context, `io.github.jaroslawdabrowski.preferences`, mirroring the same domain/port/application/adapter shape, for the single persisted language setting (`Language` enum EN/PL). `GET`/`PUT /api/preferences/language` read/write a single-row SQLite table (`PanacheLanguagePreferenceRepository`, fixed id) — this is what the frontend's language switcher persists to, instead of just `localStorage`.

### Process settings: DB-backed, not `application.properties`

Everything the planning process needs to run - SOC thresholds, battery capacity, the two per-period consumption estimates (`consumptionAfterOvernightKwh`/`consumptionAfterAfternoonKwh`; settings saved before they existed are migrated on load in `PanacheProcessSettingsRepository.migrateConsumptionEstimates` from the old daily/afternoon figures), cheap tariff windows, the two daily decision times, the PV forecast install (lat/lon + one `DirectionPanelSettings(declinationDegrees, kwp)` per `CompassDirection` - `NORTH`/`EAST`/`SOUTH`/`WEST`, azimuth fixed per direction, `kwp == 0` means no panel that way), and the inverter connection (host/port/logger serial) - lives in one `ProcessSettings` record, persisted as a single JSON blob (`ProcessSettingsEntity.settingsJson`, single-row table like `LanguagePreferenceEntity`) via `PanacheProcessSettingsRepository`. `GET`/`PUT /api/settings` (`ProcessSettingsResource`, wire shape `ProcessSettingsPayload` - same record for both directions, times as `"HH:mm"` strings) is the only way to change it; there is deliberately no compiled-in fallback/default anymore - an inverter host or logger serial baked into a properties default would be personal/hardware data checked into git (previously kept out via a gitignored `.env`; now it's just DB data, which was already gitignored).

**Nothing has been configured is a normal, expected state, not a bug**: `EnergyPlanner` loads `ProcessSettings` fresh on every call (never cached - they can change at any time) and throws `ProcessSettingsNotConfiguredException` if `ProcessSettingsPort.load()` is empty. The scheduled jobs (`DynamicEnergyPlanningScheduler.runOvernight`/`runAfternoon`) catch that specific exception and just log that nothing is configured, skipping the run - no error, no retry. The web layer instead lets it propagate to `ProcessSettingsNotConfiguredExceptionMapper`, which maps it to `409 {"error":"settings.notConfigured"}`; the frontend's `settingsAwareErrorKey()` helper (`core/settings-error.util.ts`) turns that into a specific "go configure it" message with a link to `/settings` instead of a generic fetch-failed one. Domain-level validation (SOC range, positive kWp, etc., enforced in each settings record's compact constructor) throws `IllegalArgumentException`, mapped to `400` by `InvalidSettingsExceptionMapper`.

**The overnight decision runs twice**: at `overnightTime` (21:45) and again at `ScheduleSettings.overnightRecheckTime` (default 03:30, inside the window; `null`/blank = off; older settings get 03:30 on load via `migrateOvernightRecheck`) - same `plan(OVERNIGHT)`, its period is still 06-13 of that morning, and it simply overwrites the 21:45 result with one based on a fresher forecast (the battery needs only ~2 h at 5 kW). The 21:45 run stays as the safety net if the recheck fails.

**Saving settings always re-registers both scheduled jobs**, whatever changed - `ProcessSettingsManager.updateSettings()` saves then calls `SchedulingPort.reschedule(Optional.of(settings))` unconditionally, simpler and just as correct as diffing what changed. `DynamicEnergyPlanningScheduler` implements `SchedulingPort` using Quarkus's *programmatic* `Scheduler` API (`scheduler.newJob(identity).setCron(...).setTask(...).schedule()` / `scheduler.unscheduleJob(identity)`) instead of a fixed `@Scheduled` cron, since the times are now runtime data; it also self-initializes from current settings on `StartupEvent`. Because there are now zero declarative `@Scheduled` methods anywhere, Quarkus won't auto-start its scheduler engine on its own - `quarkus.scheduler.start-mode=forced` in `application.properties` is required, or calling the `Scheduler` bean at startup throws `UnsupportedOperationException: Scheduler was not started`. This adapter plays both an "in" role (its jobs invoke `PlanOvernightChargeUseCase`/`PlanAfternoonTopUpUseCase`) and the "out" `SchedulingPort` role (the application layer calls back into it) - a pragmatic, deliberate exception to one-direction hexagonal wiring that's common for scheduler adapters.

`InverterPort` and `ForecastPort` take the relevant settings sub-record (`InverterConnectionSettings`, `ForecastSettings`) as a parameter on every call instead of the adapter reading static `@ConfigMapping` config - `SolarmanInverterConfig` now holds only protocol-level constants (register bases, `modbusSlaveAddress`, `writeEnabled`, `socketTimeoutMillis`), never host/port/serial. `ForecastSolarAdapter` calls api.forecast.solar once per direction that actually has a panel (`ForecastSettings.panelFor(direction).hasPanel()`, i.e. `kwp > 0`) and sums - a direction with no panel is skipped entirely, never called with `kwp=0`.

### Inverter integration: the protocol is fully isolated in one adapter package

Deye/Solarman stick loggers don't speak plain Modbus TCP — they wrap a Modbus RTU frame inside a proprietary "Solarman V5" envelope (start/length/control-code/logger-serial/checksum framing) over TCP, typically port 8899. That whole protocol — `SolarmanV5Frame` (envelope), `ModbusRtuFrame` (function 0x03/0x04/0x10 PDUs), `ModbusCrc16` — lives entirely in `adapter/out/inverter/solarman/`, and only `SolarmanInverterAdapter` (implementing `InverterPort`) is visible outside it. No register numbers or byte arrays should ever leak into `domain/` or `application/` — if you're tempted to reference a register address outside this package, it belongs in `SolarmanInverterConfig` instead.

**Writes must use Modbus function 0x10 (write multiple registers), not 0x06 (write single register)** - confirmed against real hardware: 0x06 is silently rejected by this inverter (a non-standard 2-byte `05 00` response, no error, but the value never actually changes - this is what caused the original "safety incident" write to look successful while doing nothing). `ModbusRtuFrame.writeMultipleRegisters(slave, register, new int[]{value})` with a one-element array is the correct way to write a single register on this device; there is no `writeSingleRegister` anymore. `ModbusRtuFrame.checkWriteMultipleRegistersResponse` validates the echo (start register + count) and raises on rejection instead of assuming success - always call it after a write.

The connection details (host/port/logger-serial - now `InverterConnectionSettings`, part of the DB-backed process settings, see below), `battery-soc-register` (holding register 588, raw value = percent, no scaling), and the TOU (Time-of-Use) register bases are all **confirmed working** against the real logger on the LAN, cross-checked against the inverter's own LCD panel. The inverter has **6 fixed TOU slots** (visible on the LCD under System Work Mode), one register per slot per field, not single global registers: Time `148–153` (HHMM, e.g. `100`=01:00), Power `154–159` (Watts - grid-charge power cap for that slot), Batt%-target `166–171`, Grid Charge enable `172–177` (confirmed live: toggling a slot's checkbox on the LCD flipped its register `0`→`1`, nothing else changed). `160–165` is an unidentified column; the Gen-enable block was never located (not needed for grid charging). `TouSlots.java` centralizes the slot-index knowledge: which of the 6 slots means what, and which slot(s) a `ChargeWindow` governs (`OVERNIGHT` → slots 5 and 0, since the night window spans midnight and is two device table entries; `AFTERNOON` → slot 2 only).

Power caps are a **static hardware setting**, not part of the daily decision - `TouSlots.powerWattsFor(window)`/`FALLBACK_POWER_WATTS` (both `POWER_WATTS` = 5000W, on **every** slot) is only read by `TouSlotSetupManualTest`, alongside the slot times. This was originally 2000W overnight / 4000W afternoon / 1000W fallback on the other slots (sized around charge speed only), but real-world observation showed the "Power" register caps **discharge speed too, not just charge**: with it low, an evening load of 3.5kW only pulled ~1kW from the battery and 2.5kW from the grid even with plenty of SOC available. Set to 5000W (the inverter's practical max) everywhere so the battery can actually cover full household load instead of being throttled - a lower cap here defeats the point of having a battery at all. The factory default was `10000` (10kW) for every slot.

**The TOU slot *times* and power caps have both been rewritten** via `TouSlotSetupManualTest.rewriteTouSlotTimesAndPowerCaps` (same manual-diagnostic pattern as `RegisterScannerManualTest` below, `@Disabled` by default - idempotent, re-run it if the device is ever reset/reconfigured) — registers 148–153 hold `TouSlots.START_TIMES_HHMM` and 154–159 hold the power caps described above, both confirmed by re-reading after the write. It requires **both** `-Dpvopt.setup.confirm=yes` and `-Dpvopt.setup.writeEnabled=true` to actually write (prints old→new and dry-runs otherwise). Getting the *time* write to actually stick is what surfaced the 0x06-vs-0x10 issue above — the inverter also has a "Lock Out All Changes" LCD setting, which turned out *not* to be the cause here (disabling it alone didn't fix the 0x06 writes) but is worth checking first if a write mysteriously doesn't persist on different hardware.

**Known flakiness: slot 5's power register (159) has twice reverted to its old value shortly after a confirmed-good write** (once to the factory 10000W, once to the previous 2000W) - re-reading immediately after the write always showed the new value, but a later read (seconds to minutes afterward) showed the old one, on both occasions fixed by simply re-running `TouSlotSetupManualTest` a second time and confirmed stable after (polled repeatedly over ~75s). Root cause not identified - possibly a device-side settings-reload racing the last write in the batch, since it's always been the last register in the 154-159 sequence that reverts. If a TOU value mysteriously doesn't match what was last written, re-run the setup tool and re-verify with a few spaced-out reads (not just the tool's own immediate re-read) before trusting it.

**Safety switch, born from a real incident**: an earlier, since-removed hourly scheduler once fired against unverified placeholder registers using the (silently-broken) 0x06 write. `SolarmanInverterConfig.writeEnabled` (`pvopt.inverter.solarman.write-enabled` - deliberately still a properties-only flag, *not* part of the user-editable JSON settings, so it can't be casually flipped from the settings UI) gates every actual Modbus write in `SolarmanInverterAdapter.applyChargeSchedule` (and in `TouSlotSetupManualTest`) — with it false, the adapter only logs what it would have written. `SolarmanInverterAdapterTest.doesNotTouchTheNetworkWhenWriteIsDisabled` is a regression guard (points the adapter at an unroutable host — RFC 5737 TEST-NET-1, passed as a fake `InverterConnectionSettings` — and asserts nothing throws, proving no socket is ever opened when disabled). The write path (both the TOU slot time rewrite and the runtime grid-charge-enable/target-SOC registers) is confirmed working end-to-end with 0x10, read back and matched. **`write-enabled` is now `true` in `application.properties`** (flipped deliberately, by the user, after the TOU slot times/power caps and the write path were verified) — the two daily scheduled jobs now write to the real inverter unattended, whenever process settings are configured. If you ever need to go back to dry-run/log-only behavior (e.g. while testing a change to the decision logic), set it back to `false` rather than relying on manual vigilance.

To find an unknown register empirically, `RegisterScannerManualTest` (in the same test package, `@Disabled` by default) reads a range of holding/input registers over real hardware and prints every value - run it with `-Dtest=RegisterScannerManualTest -DfailIfNoTests=false -Dpvopt.scan.host=... -Dpvopt.scan.loggerSerial=... -Dpvopt.scan.from=... -Dpvopt.scan.to=... -Dpvopt.scan.expectedValue=...` (and temporarily comment out its `@Disabled` - Surefire won't run a disabled test even when selected with `-Dtest`). This inverter's logger doesn't implement Modbus function 0x04 (input registers) at all - every input-register read comes back as the same 2-byte non-response - so only function 0x03 (holding registers) is useful here.

`SolarmanV5Frame`'s byte offsets were derived by cross-checking pysolarmanv5's source against a real captured response frame, and the two don't perfectly agree: encoding a request (`encodeRequest`) builds an 11-byte header + a 15-byte fixed trailer before the Modbus payload (so Modbus data logically starts at absolute offset 26), but a genuine response frame's Modbus data starts one byte earlier, at offset 25 (`MODBUS_FRAME_OFFSET`) — matching pysolarmanv5's own `v5_frame[25:-2]` decode slice. Request and response framing are apparently not symmetric in this reverse-engineered protocol; don't "fix" this apparent off-by-one without re-testing against real hardware. `SolarmanV5FrameTest` includes a fixture built from an actual captured response for exactly this reason — treat it as the source of truth over the doc comment's byte-offset table if they ever disagree.

**One exchange at a time, verified.** The stick logger serves a single TCP client and misbehaves around that: when two jobs fired together (the Mac waking and running missed jobs), responses crossed - a failed parse, a 1-register answer to a 16-register read, and a snapshot that stored SOC 2%; and even strictly one-at-a-time it has answered a request with the *previous* request's late response. So `SolarmanInverterAdapter.sendAndReceive` holds a fair `exchangeLock` for every exchange, reads exactly one frame (`SolarmanV5Frame.totalLength` from the 3-byte start, then until complete - responses can arrive in pieces), and rejects a response whose offset-5 byte doesn't echo the request's sequence low byte (`checkSequence` - offset 6 is the logger's own counter, confirmed on hardware). Reads use the strict `ModbusRtuFrame.parseReadHoldingRegistersResponse(frame, expectedCount)` (CRC + exact register count) and are retried up to 3x, 500 ms apart; writes aren't retried there (echo-checked, and the scheduler retries a whole decision). `SolarmanInverterAdapterExchangeTest` runs the adapter against a fake logger on localhost that crosses responses for overlapping clients. `EnergyRecorder` also skips a snapshot running more than 5 min after its time, or within 5 min of another (missed jobs firing in a burst on wake).

`SolarmanInverterAdapter` connects with an explicit connect-timeout (`socket.connect(new InetSocketAddress(...), timeoutMillis)`), not the bare `Socket(host, port)` constructor — that constructor blocks on the OS default TCP timeout (can be minutes) when the inverter is unreachable, which previously stalled all Vert.x worker threads on one bad request.

### Forecast: up to 4 PV planes, one API call per configured direction

The installation can have a separate panel plane per compass direction (`CompassDirection.NORTH`/`EAST`/`SOUTH`/`WEST`, each with a fixed azimuth - 180/-90/0/90 respectively, Forecast.Solar's 0=south convention). `ForecastSolarAdapter` calls api.forecast.solar once per direction whose `DirectionPanelSettings.hasPanel()` is true (`kwp > 0`) and sums the results - a direction with no panel is skipped entirely, not called with `kwp=0`. `productionProfile(period, settings)` sums, per hour slot of the period, each active direction's `watt_hours` (a cumulative-since-midnight series, reset per day) as the value at the latest timestamp ≤ `to` minus the one ≤ `from`, per day touched - if you're debugging a wrong forecast number, check `ForecastSolarAdapter.wattHoursBetween` (unit-tested) before suspecting the API response itself. **Rate limit:** the free tier allows 12 calls/hour per IP (it answers 429 beyond that, `x-ratelimit-*` headers say when it resets) and every decision costs one call per active plane, so the adapter caches each plane's response in memory for `FRESH_FOR` = 1 h and, when a call fails, falls back to the last good response for up to `USABLE_FOR` = 24 h (a response covers today and tomorrow, so the 12:45 one still serves the 21:45 decision). A series with no data for a requested day throws instead of silently reading as 0 kWh (`covers`). Only when nothing usable is left does the planner fall back to planning as if no sun were coming. The cache doesn't survive a restart.

### Security gotcha specific to this project

Basic Auth needs `io.quarkus:quarkus-security` declared explicitly in `pom.xml`. Having `io.quarkus.elytron-security-common` (for `BcryptUtil`) and `quarkus-vertx-http`'s transitive `io.quarkus.security:quarkus-security` API jar is *not* enough — that's a different Maven coordinate (groupId `io.quarkus.security`, not `io.quarkus`) providing only the interfaces, not the extension that actually wires `IdentityProviderManager` into the HTTP layer. Without the real `io.quarkus:quarkus-security` extension, `@Authenticated`, `quarkus.http.auth.permission.*`, and any custom `IdentityProvider` are silently no-ops — every request gets through regardless of credentials, in both dev and packaged/prod mode, with no warning or error logged. If auth ever appears to stop enforcing, check that `security` is still in the "Installed features" line Quarkus logs at startup.

Auth itself: single shared LAN user, configured via `pvopt.security.username` / `pvopt.security.password-hash` (BCrypt) in `application.properties` — not a properties file per the original ask, but achieves the same "hashed password in config" goal. `BasicAuthIdentityProvider` + `SingleUserSecurityIdentity` implement this with no roles/permissions (single user, so `hasRole` always returns false and isn't used).

### Persistence

SQLite via `quarkus-jdbc-sqlite` + `hibernate-community-dialects` (`org.hibernate.community.dialect.SQLiteDialect` — the jdbc-sqlite extension does not itself bundle a Hibernate dialect, that's a separate dependency). DB file at `backend/data/pvopt.db`, opened in **WAL mode with `busy_timeout=10000`** (JDBC URL params) - in the default rollback journal a reader (the dashboard loading history) blocked the 22:00 snapshot's write with `SQLITE_BUSY` and lost a measured period; WAL also adds `pvopt.db-wal`/`-shm` next to it (gitignored too); the `data/` directory must exist beforehand (SQLite won't create parent directories) — it's committed with a `.gitkeep`, the `.db` file itself is gitignored.

### Frontend

Standalone Angular components with signals, no NgModules. Auth is HTTP Basic, not session/cookie based: `AuthService` stores the `Basic <base64>` header in `sessionStorage` after a successful login probe against `/api/status`, and `authInterceptor` attaches it to every request whose URL starts with `/api`. `authGuard` redirects to `/login` when nothing is stored. There's no token refresh/expiry handling — a 401 from the backend (e.g. wrong stored credentials) surfaces as a failed API call, not an automatic redirect to login.

`quarkus.quinoa.enable-spa-routing=true` is required in `application.properties` - without it, a hard refresh (or directly opening a URL) on any Angular client-side route like `/dashboard` 404s at the Quarkus level, since Quinoa/Quarkus otherwise only serves `index.html` for `/` and falls through to a real 404 for anything else it doesn't recognize as a static asset or backend route.

Styling is our own design system in `frontend/src/styles.scss` (tokens + shared classes like `.card`, `.field`/`.input`, `.list-row`, `.chip`, `.btn-*`) - **no Angular Material components are rendered** (the `@angular/material`/`@angular/animations` packages are still in `package.json` but unused). Read `docs/DESIGN.md` before touching UI: it records the rules (every value from a scale, semantic colour roles, one colour per charge window - indigo overnight, amber afternoon, green cheap/grid-charge - sidebar on desktop / floating tab bar on phones) and the dashboard's day dial (`dashboard/day-dial.ts`). Dates are formatted with `Intl` in the UI language (`core/format.ts`), not `DatePipe`. `GET /api/inverter/tou-schedule` (read-only, live device state) backs `TouSchedule` (`frontend/src/app/tou-schedule/`), a 00-24 slot bar plus a list of all 6 TOU slots (including a computed `endTime` per slot — the adapter derives it as the next slot's start time, wrapping slot 5 to slot 0), each marked as governed by a window or fixed.

`Settings` (`frontend/src/app/settings/`, route `/settings`) is a reactive form (`FormBuilder`, nested `FormGroup`s mirroring `ProcessSettingsPayload` field-for-field) driving `GET`/`PUT /api/settings` via `ProcessSettingsApi` (`core/process-settings-api.service.ts`). `cheapTariffWindows` is edited as one comma-separated text field and split/joined at the form boundary rather than a repeatable list control, to keep the form simple. `blankProcessSettings()` seeds the form when nothing is configured yet (`configured: false` in the `GET` response) - it's just UI-side zero-values, not a value ever sent to the backend unless the user explicitly saves it. `core/settings-error.util.ts`'s `settingsAwareErrorKey()` is the shared helper other pages (`Dashboard`, `TouSchedule`) use to turn a `409 {"error":"settings.notConfigured"}` into a specific, linked "go configure it" message instead of a generic fetch-failed one - use it for any new page that calls a settings-dependent endpoint.

### i18n (English + Polish)

`@ngx-translate/core` + `@ngx-translate/http-loader`, wired via `provideTranslateService(...)` in `app.config.ts` (no NgModule). Translation JSON lives in `frontend/public/i18n/{en,pl}.json` — that's the `public/` folder (served at the site root by the Angular builder), so the loader prefix is `/i18n/`, *not* the ngx-translate default `/assets/i18n/`. Components inject `TranslatePipe` directly (standalone imports) rather than importing a shared `TranslateModule`.

Error signals in components (`Login`, `Dashboard`, `History`) hold a translation *key* (e.g. `errorKey = signal<string | null>('login.error')`), not a rendered message — the template applies `| translate` at render time so the message reflects whatever language is active. Follow that pattern for any new user-facing error state instead of setting hardcoded text.

`LanguageService` (`core/language.service.ts`) is the only place that talks to `/api/preferences/language`: `init()` (called from an `effect()` in `App` once `AuthService.isAuthenticated()` goes true — the endpoint requires Basic Auth, so it can't be loaded before login) fetches the persisted language and activates it; `changeLanguage()` (used by `LanguageSwitcher`) switches `TranslateService` immediately and persists the choice in the background. Because the preference read is behind auth, the login page itself always renders in the `provideTranslateService` default (`en`) — it can't know the saved language before the user has authenticated.
